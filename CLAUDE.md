# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Tandem** ("Program cobots, together") is a browser-based cobot programming simulator with an in-browser AI partner and a research study mode. `SPEC.md` is the design source of truth. §0 lists where the v1 build deviates from the original draft, and §20 is the acceptance check. Update SPEC.md when a design decision changes.

## Commands

```bash
npm run mock-llm                     # scripted OpenAI-compatible mock on :8787 (no API key needed)
VITE_BASE=/ npm run dev              # dev server :5173; put VITE_LLM_PROXY_URL=http://localhost:8787 in .env.development.local
npm test                             # Vitest unit tests (tests/unit)
npx vitest run tests/unit/tasks.test.ts -t kitchen-pour   # single test
npm run test:e2e                     # Playwright: builds with --mode e2e, starts mock LLM + vite preview on :4173
npx playwright test tests/e2e/study.spec.ts               # single E2E file
npm run test:functions               # functions + Firestore rules in Firebase emulators (needs Java)
npm run lint && npm run typecheck
npm run build                        # docs index → tsc → vite build (VITE_BASE defaults to /Tandem/)
npm run docs:index                   # content/docs/*.md → src/agent/docs-index.json (re-run after editing docs)
VITE_BASE=/ npm run dev  →  /?editor # Tandem Studio: build environments, tasks, experiments, arms (dev server only; saves into content/)
npx tsx scripts/gen-codes.ts --experiment pilot --per-condition 10 --dry-run   # participant codes + links (Studio > Experiments does it with buttons)
npx tsx scripts/make-example-models.ts  # regenerate public/models/examples (format references)
npx tsx scripts/record-clips.ts      # re-record public/clips/*.gif + landing thumbnails (needs mock-llm + a VITE_E2E dev server on :5180; see file header)
npx tsx scripts/record-clips.ts --thumbs-only   # only the missing landing thumbnails (e.g. after adding a demo level)
```

`/` is the landing page; the app is at `/?demo` (`?demo=<taskId>`, `&tour`). Without Firebase configured, `/?code=TEST-SUGGEST-1` (or `TEST-QA-n` / `TEST-OFF-n`, optionally `-<EXPERIMENT-ID>` such as `TEST-OFF-1-DUO-PILOT`) starts a local study session that logs to IndexedDB. In dev and E2E builds, `window.__tandem` exposes `{ useApp, host, programSource, updateWorkspace }`, plus `window.__tandemSetSteps(steps)`, `window.__tandemSetLanes({ A: [...], B: [...] })` and `window.__tandemBlockly = { ws, Blockly }` for driving the app from tests.

## Architecture

- **`src/sim/` is pure, headless and deterministic (lint-enforced).** It must not import three/React/Blockly/store, use `Math.random` (use `rng.ts` with its state kept in `SimState`), or read `Date`/`performance`. The same `SimCore` runs live (`src/simHost.ts`), in the dry-run worker, and in unit tests.
  - Internal units are meters and radians. The user API, UI and agent views use millimeters and degrees.
  - Sim time advances only while a command executes. Keep it that way: the determinism test compares full `RunTrace` JSON.
- **Kinematics.** Arms are a link chain where each link's local transform = `pre · J(q) · post` (`src/sim/kinematics/arm.ts`). DH arms are converted at load. The KR5 and T6 chains in `content/arms/*.json` were generated by `scripts/convert-uaibot.ts` to reproduce UAIbotJS's Object3D quirks, so the vendored meshes (`public/models/uaibot`, placement table in `src/view/robotVisual.ts`) line up. Don't "clean up" those chains, or the meshes will misalign. The parity test lives in `tests/unit/kinematics.test.ts`.
- **Faults are pre-checks.** `SimCore.begin()` plans and validates the whole motion (IK every 2 mm, joint jumps, manipulability, capsule-vs-OBB collision) before the robot moves. Collision capsules are generated from link-frame origins plus `linkRadius`. Fixtures tagged `mount` are ignored by the first two segments.
- **Execution path.** Run goes through `ProgramRunner` (main thread), which creates a per-run `program.worker.ts` with network globals deleted. Robot calls are postMessage RPCs (`runtime/protocol.ts`) executed on the live SimCore from the render loop (`host.frame`).
  - `runtime/robotApi.ts` is shared with `runtime/headless.ts` (dry runs and tests), so API changes happen in one place.
  - Fault lines come from `user-program.js` sourceURL stack frames. Block highlighting uses Blockly `STATEMENT_PREFIX` → `__hl(id)`.
- **One API, three descriptions.** If you change the robot API, update `runtime/robotApi.ts`, `editor/robotApiDts.ts` (Monaco typings), `content/docs/*.md` (then `npm run docs:index`), the block generator in `blocks/definitions.ts`, `blocks/steps.ts` (`stepsToJs`), and the system prompt (`agent/prompts/system.vN.ts`, bumping `PROMPT_VERSION`).
- **Multi-arm (SPEC §21).** A scene with `robots` is a multi-arm cell (one robot "A" otherwise; there is one code path). Keep these straight:
  - Sim state is `s.robots[id]`. SimCore's single-arm methods take an optional robot id defaulting to the first robot. Each arm's joints, TCP and targets are in its own base frame (`baseOf(id)` maps to world); objects and fixtures are in world.
  - Runs have one lane (program) per robot. `runtime/scheduler.ts` decides when calls begin and when time advances: time only moves while no lane is computing, so traces stay deterministic. Live (`ProgramRunner`) and headless (`runHeadless`, which takes a string or `{ [robotId]: src }`) share it.
  - `sync()` / `robot.moveTogether()` / `robot.follow()` pair by position across lanes. Arm-vs-arm collision is a timed pre-check in `SimCore.armClash`.
  - Blocks: one Blockly workspace with a `lane_start` column per arm. `blocks/lanes.ts` keeps sync twins and alignment; it changes blocks with Blockly events disabled, because events arrive asynchronously and would look like user edits. The agent's format is `{ "lanes": { "A": [steps] } }`.
  - Workspaces keep per-arm code/targets in `ws.lanes`; use `laneTargets()` / `updateLane()`. Multi-arm reference solutions mark each arm with `// @lane A`.
  - Multi-arm tool parameters and the prompt's multi-arm section are added only on multi-arm tasks, so single-arm study conditions see unchanged text.
- **Blocks** compile one way to JS. The agent reads and proposes block programs as compact JSON "steps" (`blocks/steps.ts`), which are validated against known targets and signals before anything is shown to the user.
- **Content is data.** Arms, scenes, tasks and experiments live in `content/**/*.json`, validated by zod in `src/content/index.ts`. Every task has a reference solution in `tests/fixtures/solutions/<task>.js` that must pass (only `passOn: "live"` tasks may skip it). Add one when you add a task, because it is how scene geometry gets validated. Blocks tasks can start from a program (`starter.steps`, JSON steps): a partial one to finish or a buggy one to fix; `tests/unit/starters.test.ts` must show the starter fails, the fix passes, and each bug matters on its own. Tandem Studio (`src/studio/`, `?editor`) authors all of this and enforces the same rules. The demo level list is `DEMO_TASKS`, the tasks with `demo.order`; never hard-code task lists.
- **3D models are visual only.** `MeshRef` on fixtures, objects, conveyor spawns and arm `visual.source: "mesh"` are drawn by `src/view/meshes.ts`. Physics keeps using boxes, cylinders and capsules, so never make collision or predicates depend on mesh geometry. URDF conversion is in `src/content/urdf.ts`.
- **No emojis in UI text** (blocks use SVG icons from `ICONS` in `blocks/definitions.ts`). Only the AI partner's replies may use them.
- **UI.** Two views: `view/Viewport.tsx` (3D cell + cell-level controls) and `pendant/Pendant.tsx` (teach pendant). The pendant shows one screen at a time (`useApp.pendantScreen`, navigate with `go()` from `pendant/screens.tsx`), with hardware run keys underneath. The Program screen is never unmounted, so Blockly state and the generated JS survive navigation. The AI partner (`panels/ChatPanel.tsx`) is a status-bar button (`AgentButton`) plus a draggable floating window (`AgentDock`). Its modals are portaled to `document.body`, because `backdrop-filter` ancestors trap `position: fixed`. E2E helpers `pendant(page, 'Jog')` and `openAgent(page)` navigate the UI. Demo task jumps go through the top-bar bubbles (`getByRole('button', { name: /^Task 2:/ })`).
- **Audio** (`src/audio/`) is all WebAudio synthesis: `sound.ts` (effects, wired by `initSound()` through a global pointer listener and a store subscription; `soundFrame()` is called from the render loop for the motor hum) and `music.ts` (demo-only generative music, or `public/music/theme.mp3` if present). Headless Chromium's realtime audio clock is unreliable, so verify synthesis with an `OfflineAudioContext` render instead.
- **Landing / routing**: `main.tsx` picks the landing page (`src/landing/`, lazy, must not import Blockly/Monaco/LangChain) or the app (`?demo`, `?code`, `?study`). The hero replays reference solutions through `runHeadless({ onStep })`.
- **Tour** (`src/tour/`): steps in `steps.ts` target `data-tour="…"` attributes (the spotlight carries `data-target`, which the E2E helper clicks). If you rename or move those elements, update the steps. It's required in study mode (untimed; task 1 restarts after it), so E2E study flows call `finishTour(page)`.
- **AI partner** (`src/agent/`) is a LangGraph.js ReAct graph (≤ 8 tool calls per turn) in the browser, calling OpenAI through `ChatOpenAI` pointed at the Firebase `llmProxy`, with `useResponsesApi: false`.
  - Tools are gated by agent mode (`off` / `qa` / `suggest`) and by per-condition `features` (`visuals`: `show_blocks`/`show_example`; `plans`: `make_plan`; `preview`: `preview_proposal` ghost replay). All features are on in the demo. Visual messages are queued until their tool's status pill appears.
  - GIFs come only from the curated list in `agent/clips.ts`, which must match `public/clips/*.gif`.
  - The agent never edits directly: `propose_patch` auto dry-runs and creates a proposal card that the user accepts or rejects.
  - `jsonProtocol.ts` is the fallback for models without tool calling.
- **Backend** (`functions/src`): `llmProxy` and `redeemCode` (HTTPS `onRequest`).
  - All key handling, the model lock for study participants, quotas (per uid, per IP hash, global demo budget) and the kill switch are server-side.
  - The function never logs prompt content.
  - Firestore rules (`firestore.rules`) let clients only create log batches and read/write their own checkpoint.
- **Participant codes** (`scripts/lib/codes.ts`, shared by `scripts/gen-codes.ts` and Studio's `/__studio/codes/*`): the service-account key lives in gitignored `keys/` (also in Vite `server.fs.deny`) and is only read server-side; never send it to the browser or log it. Re-generating continues each condition's `orderIndex`.
- **Study logging.** `study/logger.ts` sends events to an IndexedDB queue, then flushes them as batched Firestore docs (`sessions/{sid}/batches`) with a monotonic `seq`. New event types go in `study/events.ts`. The logger scrubs JWT- and API-key-shaped strings, so never log tokens or IPs. Demo mode logs nothing.

## Testing notes

- Tests never call a real LLM. Agent flows are scripted in `tests/fixtures/mock-llm/scenarios.json`: the scenario is chosen by regex on the user message, and the step index is the number of assistant turns since then. The functions emulator reaches the same mock via `LLM_UPSTREAM_URL` in `functions/.env.demo-tandem`.
- The Functions emulator reflects every CORS origin itself, so the CORS deny path is covered by a unit test (`functions/test/cors.test.ts`).
